# ADR 0012: Слои, контракт модуля и стиль Vue

- **Статус:** принято
- **Дата:** 2026-11-12
- **Область:** `src/`, `src-tauri/src/`, правила проекта

## Контекст

Правила из соседнего Nuxt-проекта переносят три разных понятия под одним
словом «слой»: механизм Nuxt-layers, направление зависимостей между
каталогами и функциональную единицу (модуль). В Tauri механизма Nuxt-layers
нет, поэтому переносить нужно не механику, а дисциплину зависимостей.

Одновременно нужно зафиксировать стиль Vue: в перенесённых правилах
запрещён Composition API и `<script setup>`, а существующий код и документация
PrimeVue 4 написаны именно так.

## Решение

1. **Vue: Composition API + `<script setup>`.** TypeScript strict. Options API
   не используется. Это единственный пункт перенесённых правил, заменённый
   на обратный.

2. **Шесть слоёв интерфейса, зависимости только вниз:**

```text
contracts → core → ui → { tools | shell } → app
```

- `contracts` — типы, пересекающие слои: топики, дескриптор инструмента,
  раскладка вкладки, шаблон, запись журнала.
- `core` — инфраструктура без Vue: мост в Rust, журнал, настройки,
  рабочее пространство.
- `ui` — preset темы и презентационные примитивы (сетка, рейл).
- `tools/<id>/` — инструмент целиком: `api.ts`, `use*.ts`, `*View.vue`.
- `shell` — сайдбар, вкладки, оболочка рабочего пространства.
- `app` — composition root: `App.vue`, `main.ts`, сборка реестра.

`tools` и `shell` не импортируют друг друга. Оболочка получает инструменты
через реестр, собранный в `app`, и рендерит по `component`.

3. **Rust зеркально:** `lib.rs` → `modules` → `core`. `core` не знает имён
   модулей. Регистрация — одна строка в `modules::register_all`.

4. **Модуль — единица композиции и удаления:**

```text
src/tools/ping/            index.ts, PingView.vue, usePing.ts, api.ts
src-tauri/src/modules/ping.rs   impl Module
```

- импортирует только `contracts`, `core`, `ui`;
- с другими модулями говорит только через шину;
- удаление — стереть папку и две строки регистрации;
- `id` совпадает с Rust-модулем, **если** Rust-часть существует.

5. **Соответствие реестров один-к-одному не требуется.** Инструмент может
   быть чисто фронтовым (секундомер, заметки), тогда Rust-обработчика нет
   и быть не должно. Обратный случай — обработчик без пункта меню — безвреден.
   Отдельного `modules.json` и проверок на равенство списков нет: третье
   место для обновления увеличило бы поверхность ошибки.

6. **Сбой вызова виден.** Ошибка `invoke` попадает в журнал и в панель
   инструмента. Молчаливой кнопки, которая ничего не делает, быть не должно.

7. **Транспорт отделён от сценария.** Инструмент не вызывает `invoke`
   напрямую: только через свой `api.ts`, который опирается на мост в `core`.
   Состояние операции гранулярное (`status.<операция>.loading/error`),
   монолитного `isLoading` нет.

8. **CSS.** Токены живут в PrimeVue preset (`src/ui/theme.ts`). Свой CSS
   описывает только оболочку и сетку; собственные переменные — с префиксом
   `--ag-`, это именные токены проекта. Компоненты PrimeVue не оборачиваются
   без общей логики.

## Почему так

- **Слои переносятся по смыслу, а не по имени.** Нумерованные слои
  (`1.base`, `2.ping`) выражают порядок, а модули — ровесники: ни один
  не может импортировать другой, и номер здесь врал бы о зависимостях.
- **Изоляция `tools ↔ shell` сильнее Nuxt-овского `app ↔ server`.** Оболочка
  не знает инструментов, инструменты не знают оболочки; связывает их только
  реестр в `app`.
- **`<script setup>`** даёт точный вывод типов в `vue-tsc`, меньше шума и
  совпадает с примерами PrimeVue. Options API пришлось бы поддерживать
  вопреки экосистеме.
- **Отказ от проверки реестров** следует из того, что списки не обязаны
  совпадать. Проверка защищала бы от ошибки, которой в модели нет.

## Последствия

- Новый инструмент — это папка в `src/tools/` и, при наличии поведения
  в Rust, файл в `src-tauri/src/modules/` плюс две строки регистрации.
- Импорт из `tools/a` в `tools/b` запрещён; при необходимости общего кода
  он опускается в `core` или `contracts`.
- Правила Nuxt переносятся выборочно: без нумерованных слоёв, `app/server`,
  авто-импортов composables, `--ag-*` токенов и порога мутаций.
- Стиль файлов: `.ts` — camelCase, `.vue` — PascalCase (`HomeView.vue`).
  Правило Nuxt «все файлы camelCase» к компонентам не применяется.
- Тесты Rust остаются в `#[cfg(test)] mod tests` внутри файла: правило
  «тесты только в отдельной папке» — идиома Nuxt, не Rust.

## Отклонённые альтернативы

- **Нумерованные слои (`0.utils`, `5.domain`) и папка на модуль.**
  В Vite нет слияния конфигов и авто-импорта, поэтому слой стал бы просто
  папкой; нумерация при этом задавала бы ложные зависимости между
  модулями-ровесниками.
- **Options API по правилам Nuxt-проекта.** Переписывание существующих
  экранов и расхождение с документацией PrimeVue без выигрыша.
- **Проверка равенства реестров через `modules.json`.** Третье место для
  синхронизации и запрет на чисто фронтовые инструменты.
- **Обёртки над компонентами PrimeVue.** Слой, который придётся
  синхронизировать с библиотекой; обёртка только под общую логику.
- **Свой мини-кит вместо PrimeVue.** Отвергнуто в ADR 0009.
