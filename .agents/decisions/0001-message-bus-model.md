# ADR 0001: Модель шины — события, команды и `ask`

- **Статус:** принято
- **Дата:** 2026-11-10
- **Область:** `src-tauri/src/core/`, все подсистемы

## Контекст

Платформа строится как набор слабосвязанных подсистем. За образец взята
архитектура `max40in/Max40in`: CQRS, шина сообщений, строгий порядок
инициализации, внедрение зависимостей.

В образце два примитива: **Command** (один обработчик, синхронно) и **Event**
(много обработчиков, асинхронно). Возник вопрос: не являются ли команды
рудиментом, если система в основном событийная? У разработчика образца есть
мнение, что команды почти не нужны.

При этом есть требования, которые на чисто событийной модели ломаются:

- приложение живёт в трее и закрывается из меню по правой кнопке;
- перехват закрытия окна требует **немедленного** решения `prevent_close()`;
- корректное завершение должно дождаться обработки очереди событий;
- интерфейсу нужен результат операции (например, DNS-поиска) и её ошибка.

## Решение

1. **Event — основной путь.** Уведомления, результаты долгих операций,
   реакции на изменения. Доставка асинхронная, подписчиков много, ошибка
   одного подписчика не мешает остальным.
2. **Command — узкий примитив для императивных операций.** Жизненный цикл,
   трей, окна, настройки, отмена задач, горячие клавиши. Синхронно, ровно один
   обработчик, ошибка возвращается вызывающему. Второй обработчик на ту же
   команду отвергается при регистрации.
3. **`ask` — надстройка над событиями, а не третий тип сообщения.** Шина
   добавляет в нагрузку `correlation_id`, публикует событие-запрос и ждёт
   событие-ответ с тем же идентификатором и **явно указанным топиком ответа**.
4. **Правило разделения:** событие — когда достаточно «сообщить»; команда —
   когда нужно «сделать сейчас и узнать результат».

## Почему так

Чисто событийная модель не подходит по трём причинам:

- **Закрытие окна.** `WindowEvent::CloseRequested` — синхронный обработчик
  ОС-потока. Решение «свернуть в трей» нужно принять до того, как окно
  закроется; асинхронное событие может не успеть.
- **Остановка шины.** `bus.stop()` делает `join()` потока-диспетчера. Если
  «выход» смоделировать событием, его обработчик выполнится **внутри**
  диспетчера и попытается дождаться самого себя — дедлок.
- **Результат для интерфейса.** Команда возвращает ошибку вызывающему, а
  событие глушит её в лог. Для кнопки «сделать» это неприемлемо.

`ask` закрывает потребность UI в «обещании» результата, не вводя третий
примитив: это соглашение поверх событий, а не отдельный механизм.

## Последствия

- События остаются обычным путём; команды не превращаются в «вторую шину».
- У каждой команды должен быть ровно один владелец — это проверяется в
  `subscribe_command`.
- `ask` блокирует вызывающий поток до ответа или таймаута. В Tauri вызов идёт
  на потоке команды, поэтому интерфейс не замирает.
- Новая императивная операция оформляется командой, а не событием с флагом.

## Отклонённые альтернативы

- **Только события.** Не проходит по `prevent_close()` и по остановке
  диспетчера (дедлок); UI не получает ошибку операции.
- **Единый `Message` с полем «режим доставки».** Поведение начинает зависеть от
  рантайм-значения: один и тот же тип ведёт себя по-разному, ошибки
  обрабатываются по-разному. Статическая типизация перестаёт помогать.
- **Команды для всего.** Теряется главное преимущество событий — много
  независимых подписчиков и изоляция ошибок.
- **`ask` без `reply_topic`.** Запрос сам несёт `correlation_id`, поэтому шина
  принимала его за ответ и возвращала эхо запроса. Проверка топика ответа
  обязательна.
