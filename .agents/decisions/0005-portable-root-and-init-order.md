# ADR 0005: Портативный корень, проверка записи и порядок инициализации

- **Статус:** принято
- **Дата:** 2026-11-12
- **Область:** `src-tauri/src/core/storage.rs`, `src-tauri/src/core/settings.rs`,
  `src-tauri/src/lib.rs`, интерфейс (блокирующий экран)

## Контекст

Приложение переносимое: всё состояние лежит рядом с исполняемым файлом. Рядом
живут `settings.json` и папка `logs\`.

Если папка недоступна для записи (программа в `Program Files`, съёмный носитель
с защитой, чужой профиль), ломается не только лог: не сохраняются настройки,
нельзя обновить конфигурацию модулей, а позже — кеш и история. То есть это
условие существования приложения, а не деталь логгера.

Одновременно нужно назвать слой, в который попадают такие вещи, как хранилище,
настройки и логирование: это не ядро и не модули.

## Решение

1. **Три слоя.**

| Слой | Что входит | Пункт меню | Можно убрать |
|---|---|---|---|
| Ядро | шина, `Deps`, `EventSink`, трейт модуля | нет | нет |
| Сервисы ядра | хранилище, настройки, логирование, трассировка, жизненный цикл окна, трей | нет | нет |
| Модули | ping, dnslookup, будущие утилиты | да | да |

**Сервис ядра** — инфраструктурная часть, без которой приложение не работает:
живёт в `core/`, кладёт себя в `Deps`, своего экрана в меню не имеет.

2. **Портативный корень — папка исполняемого файла.** Отката в
   `%LOCALAPPDATA%` нет: если писать некуда, приложение не работает.

3. **Проверка записи — метод хранилища.** Не эвристика по атрибутам, а проба
   делом: создать `logs\`, записать и удалить пробный файл. Проверка выполняется
   в `setup()` до запуска шины.

4. **Провал проверки — блокирующий экран.** Интерфейс получает статус и вместо
   модулей показывает: «Не могу писать в папку программы», путь, что сделать
   (перенести папку, снять атрибут «только чтение»). Модули не стартуют. Кнопка
   «Выйти» продолжает работать.

5. **`settings.json` рядом с exe, минимальный.** Пока в нём одно поле —
   `log_level`. Общий сервис настроек появится, когда полей станет больше
   одного: схема, спроектированная под один ключ, на втором всё равно
   переделывается.

6. **Строгий порядок инициализации.**

```text
storage → settings → logging → bus → sink → modules → bus.start()
```

`storage` первым, потому что он единственный знает, **куда** писать.
`settings` читает уровень, но ещё не может логировать. `logging` стартует с уже
известными уровнем и путём. Дальше как раньше.

## Почему так

Портативная утилита, которая «вроде работает», но не запоминает настройки и не
оставляет логов, хуже, чем утилита, которая сразу говорит «положи меня в
доступное место». Молчаливая деградация удваивает число состояний приложения
ради сценария, который пользователь всё равно захочет исправить.

Проверка делом, а не по атрибутам: атрибут «только чтение» не описывает всех
причин отказа (права ACL, сетевой диск, политика). Единственный надёжный
ответ — попробовать записать.

Порядок инициализации следует из зависимости: логирование не может стартовать
раньше, чем известно, куда писать.

## Последствия

- Пути к настройкам и логам выдаёт только хранилище; в `lib.rs` нет ни одной
  самодельной проверки прав.
- При недоступной папке состояние настроек не сохраняется, и это видно на
  экране, а не выясняется при разборе поломки.
- `bus.stop()` остаётся единственным местом, требующим потока событийного цикла;
  сервисы ядра не создают собственных циклов завершения.

## Отклонённые альтернативы

- **Откат в `%LOCALAPPDATA%\ToolBox\`.** Теряется переносимость: копируешь
  папку на флешку, настройки остаются на старой машине. Плюс два места записи.
- **Деградация с баннером.** Работает «наполовину», число состояний удваивается.
- **Проверка по факту первой неудачной записи.** Минимум кода, максимум
  сюрпризов — ровно та слепая зона, из-за которой всё затевалось.
- **Полноценный сервис настроек сразу.** Лишний слой под одно поле.
- **Плоская структура «ядро + модули».** Хранилище, настройки и логи некуда
  положить по правилу; их пришлось бы либо называть модулями, либо оставлять без
  статуса.
