# ADR 0061: Удаление данных и корзина

- **Статус:** принято
- **Дата:** 2026-11-20
- **Область:** `src-tauri/src/core/services/trash.rs`,
  `profiles.rs`, `presets.rs`, `languages.rs`,
  `src-tauri/src/core/commands/`, `src-tauri/src/core/store/storage.rs`,
  `src-tauri/src/lib.rs`, `.agents/rules/project/quality.md`,
  `.agents/rules/project/i18n.md`, `README.md`, `.agents/GLOSSARY.md`,
  тексты `dnslookup.preset.removed`

## Контекст

Удаление сложилось по частям и разошлось в разные стороны:

- профиль уходил в `local/trash/<id>/`, без общей категории;
- пресет - в `local/trash/presets/<tool>/`, без профиля-источника;
- внешний словарь - в `local/trash/languages/`;
- свой DNS-сервер удалялся перезаписью `servers.json`, без подтверждения;
- рабочее пространство и логи удалялись без корзины;
- README и глоссарий обещали в корзине «данные инструментов», хотя раздела
  данных нет с ADR 0056;
- корзина была невидимой, но текст уведомления обещал перенос в неё;
- `local/` не синхронизируется по ADR 0010, но README об этом молчал.

Отдельная ловушка обнаружилась при проверке: `rename` сохраняет время
изменения. Профиль, последний раз изменённый месяц назад и удалённый
сегодня, по mtime уже старше 14 дней и был бы удалён при первом запуске.

## Решение

1. **Удаление делится на три режима.**

   - **Файловая сущность** - профиль, пресет, внешний словарь, целый файл
     данных инструмента. Удаляется после подтверждения переносом в корзину.
     Исходник при отказе переноса остаётся на месте.
   - **Запись внутри документа** - свой DNS-сервер, строка таблицы, значение
     настройки. Удаляется правкой документа, без корзины и без отдельного
     подтверждения.
   - **Машинное состояние и производные файлы** - рабочее пространство, логи,
     `*.updates.jsonc`, прежний `*.missing.jsonc`, `*.tmp`, осиротевшие
     файлы. Удаляются сразу, без корзины. Подтверждение нужно только
     массовой очистке по явной кнопке.

2. **Корзина - внутренняя страховка.** В интерфейсе нет входа, списка
   и восстановления. Уведомления и подтверждения называют предмет и действие,
   но не обещают возврат. Папка `trash` не входит в список открываемых папок
   и в `FolderKind`.

3. **Корзина лежит в `local/trash/`.** `local/` принадлежит машине
   и не синхронизируется. Удаление на одной машине не приезжает на другую
   как новая папка. Приложение не настраивает синхронизацию и не проверяет
   её: это условие записано в README.

4. **Верхний уровень корзины - единица удаления, ниже - происхождение.**

   ```text
   local/trash/
     profiles/<id>/                       профиль удалён целиком
     presets/<profile>/<tool>/<id>.json   отдельный пресет
     languages/<code>.jsonc               внешний словарь
   ```

   Профиль и пресет не смешиваются в одной ветке. Профиль с названием
   `presets` лежит в `profiles/presets/` и не занимает категорию пресетов.

5. **Перенос, а не копирование с удалением.** Совпадение имени не
   перезаписывает корзину: свободное имя получает `-2`, `-3`. Повреждённый
   пользовательский файл не удаляется: показывается ошибка.

6. **Срок - 14 дней от удаления.** `rename` сохраняет mtime, поэтому после
   переноса запись получает время удаления. Чистка идёт при старте и после
   каждого удаления, без фонового таймера. Единица чистки - то, что
   перенесли: папка профиля целиком, файл пресета, файл словаря. Пустые
   промежуточные папки убираются. Отказ чистки пишется в лог и не блокирует
   запуск.

7. **Старую корзину не мигрируем.** Плоские `trash/<id>`,
   `trash/presets/<tool>/` и `trash/languages/` чистятся по сроку.
   Происхождение старых пресетов уже потеряно, миграция его не восстановит.
   Через 14 дней остаётся только новая раскладка.

8. **Переиспользование id профиля приемлемо.** После удаления профиля его id
   может достаться новому профилю. Тогда `trash/presets/<id>/` содержит
   пресеты двух поколений. Файлы не перезаписываются, но происхождение
   по id уже не различить. Для внутренней страховки это терпимо: даты в пути
   не вводим.

9. **Сначала убираются ссылки, потом переносится файл.** При удалении пресета
   указатель «по умолчанию» снимается до переноса: иначе при отказе переноса
   в `profile.json` осталась бы ссылка на удалённый файл. При возврате языка
   файл изменений удаляется до переноса словаря. При удалении профиля
   рабочее пространство убирается после переноса, а осиротевшее - при старте.

10. **Списки - это правка документа.** Свои DNS-серверы, строки таблицы
    и значения настроек не попадают в корзину: корзина двигает файлы,
    а не поля JSON.

## Почему так

- **`local/` не синхронизируется.** Корзина внутри `profiles/` вернулась бы
  с другой машины как живые файлы, попала бы в списки и статистику.
- **Верхний уровень по единице удаления.** Вложенный вариант
  `trash/profiles/<id>/presets/` создаёт частичную папку профиля, а при
  удалении профиля целиком появляется `work-2`. Один профиль разъезжается
  на две папки, хотя ничего не потеряно.
- **Внутренняя корзина не создаёт мёртвого обещания.** Кнопка «Открыть
  корзину» и восстановление потребовали бы экрана, правил и поддержки;
  страховка на 14 дней решает исходную задачу дешевле.
- **14 дней ограничивают рост.** Ручная чистка недоступна, бессрочное
  хранение копило бы удалённое без предела.
- **Отметка времени обязательна.** Без неё старый файл, удалённый сегодня,
  исчезает при первом запуске. Это не теория: mtime после `rename`
  не меняется.
- **Разные ветки сохраняют происхождение.** Пресет из `work` лежит
  в `presets/work/`, а не в общем `presets/<tool>/`; при нескольких профилях
  ручной разбор не превращается в угадывание.

## Последствия

- README и глоссарий больше не обещают данных инструментов в корзине
  и описывают `local/` как машинное состояние.
- Уведомление о пресете говорит «удалён», а не «перемещён в корзину».
- `Storage` знает `profiles_trash_dir()`; `presets_trash_dir()` означает
  `local/trash/presets/`, внутри - профиль и инструмент.
- Появляется сервис `trash` с отметкой времени и автоочисткой; чистка
  вызывается из точки сборки и команд удаления.
- Тесты проверяют: старый профиль, удалённый сегодня, переживает чистку;
  профиль с именем `presets` не сталкивается с категорией; одинаковый id
  пресета из разных профилей не смешивается; старая раскладка чистится.
- Удаление не стирает данные сразу: копия лежит на диске до 14 дней.
  Безопасное стирание не обещается.
- Ручное восстановление возможно, пока запись не удалена, но не
  поддерживается и не обещается.
- Если синхронизируется весь корень, корзина синхронизируется вместе с ним.
  Приложение это не проверяет.
- Старые заметки `.scratch/*` не являются памятью проекта: их удаление
  не уменьшает понимание.

## Отклонённые альтернативы

- **Корзина внутри `profiles/<id>/presets/`.** Синхронизация вернула бы
  удалённое, список пресетов увидел бы «удалённый» файл, статистика профиля
  посчитала бы его живым.
- **Корзина как пользовательская функция с кнопкой и восстановлением.**
  Требует экрана, правил восстановления и обещания, которого нет.
- **Плоские категории `trash/<id>` и `trash/presets/<tool>/`.** Теряется
  профиль-источник, а профиль с именем `presets` занимает имя категории.
- **Корзина для записей документа.** Пришлось бы хранить теневые копии
  JSON-полей: корзина двигает файлы, а не записи.
- **Только ручная чистка.** Корзина растёт без предела, а входа в неё нет.
- **Хранить корзину бессрочно.** Удалённые данные копятся на диске.
- **Системная корзина ОС.** Уводит данные из переносимой папки программы
  и зависит от платформы.
- **Дата удаления в пути.** Решает переиспользование id, но добавляет
  машинерию и ломает предсказуемые пути ради редкого случая.
- **Завести `trash/data/` заранее.** Ветка без писателя - обещание без
  механизма; появится вместе с удалением целого файла данных.
