# ADR 0010: Хранение состояния — файлы, профили и границы синхронизации

- **Статус:** принято
- **Дата:** 2026-11-12
- **Область:** `src-tauri/src/core/store/storage.rs`, `src-tauri/src/core/services/settings.rs`,
  `src-tauri/src/lib.rs`, сервис данных инструментов, раскладка папки программы

> Дополнение: точный путь рабочего пространства изменён ADR 0050
> (`local/workspaces/<id>.json`), шаблоны вкладок удалены ADR 0046,
> их место заняли пресеты настроек (ADR 0030). Остальные решения этого ADR
> в силе; раскладка ниже показана по текущему состоянию.

## Контекст

ADR 0005 ввёл портативный корень и один `settings.json` с уровнем лога.
Дальше появляются профили (работа, дом, заказы), шаблоны вкладок и данные
инструментов — например, списки для dnslookup.

Одновременно действуют три внешних обстоятельства:

- папку с программой могут положить на сетевую шару;
- владелец может синхронизировать её через Syncthing между своими машинами;
- коллеги не будут настраивать синхронизацию: они скопируют папку целиком
  и будут жить со своей копией.

Ранее для данных инструментов рассматривался SQLite. От него решено
отказаться: синхронизация файловая и без слияния, поэтому база превращается
в «победила одна версия, остальные изменения исчезли».

## Решение

1. **Никакого SQLite.** Данные инструментов — JSON-документы, по файлу
   на сущность. Что именно инструмент хранит (списки, настройки, результаты)
   и сколько живёт это состояние, решается при проектировании инструмента
   и в это решение не входит.

2. **Раскладка папки программы.**

```text
toolbox.exe
local/                        не синхронизируется, принадлежит машине
  settings.json               окно, тема, сайдбар, уровень лога, активный профиль
  workspaces/<id>.json        открытые вкладки профиля (ADR 0050)
  logs/                       файловый лог
profiles/                     синхронизируется, принадлежит пользователю
  work/
    profile.json              название профиля и указатели пресетов
    presets/<tool>/<id>.json  пресеты настроек инструментов
    data/<tool>/<name>.json   данные инструментов (списки DNS)
  home/
```

3. **Граница синхронизации проходит по частоте и владельцу.** Частое
   и машинное — в `local/`. Редкое и пользовательское — в `profiles/`.
   Настройки и открытые вкладки не переезжают между машинами; шаблоны
   и данные — переезжают.

4. **Один файл — одна сущность.** Имя файла — стабильный id, название лежит
   внутри документа. Переименование не двигает файл, конфликт затрагивает
   одну сущность, а не весь набор.

5. **Профиль — папка.** Список профилей — содержимое `profiles/`, отдельного
   реестра нет. Активный профиль хранится в `local/settings.json`.
   Переключение профиля записывает его и перезапускает приложение: у инструментов
   уже загружены данные профиля, и половина состояния из «работы», половина
   из «дома» хуже, чем перезапуск на пару секунд.

6. **Атомарная запись.** Все документы пишутся во временный файл `*.tmp`
   в той же папке и переименовываются. Открытых файлов, кроме лога, нет.

7. **Синхронизация не контролируется.** Приложение не отличает
   синхронизируемую папку от обычной: не ищет `.stfolder`, не читает
   `.stignore` и не показывает состояние Syncthing. Синхронизация — внешний
   сценарий использования папки, а не функция программы.
   Из файлов пропускаются только собственные временные `*.tmp`: иначе
   недописанный файл попал бы в список шаблонов или данных.
   Конфликтная копия `*.sync-conflict-*` остаётся обычным файлом в папке;
   приложение о ней не знает и разбирает её как ещё один документ.

8. **Кто пишет.** Rust — единственный, кто трогает диск: `storage` знает пути,
   `settings` — типизированные настройки, сервис данных — документы
   инструментов. Vue присылает и забирает JSON, не зная путей.

## Почему так

- **Файл — единица слияния.** Syncthing умеет сравнивать и копировать файлы,
  но не строки в базе. Один список в одном файле конфликтует только сам с собой.
- **Копирование папки остаётся рабочим сценарием.** Коллеге достаточно
  скопировать каталог: все пути относительны, ничего не прописано в системе.
- **JSON читается глазами.** Список DNS можно открыть и поправить без
  приложения; повреждённый файл лечится вручную.
- **Нет миграций и нативной зависимости.** Схема — поле `version` в документе;
  rusqlite со встроенным SQLite не нужен.
- **Объёмы человеческие.** Списки — сотни строк, а не миллионы записей.
  Перезапись файла целиком дешевле, чем поддержка базы.

## Последствия

- Тема, уровень лога и открытые вкладки не синхронизируются между машинами.
  Если понадобится — соответствующее поле выносится отдельно, это дешёвая
  миграция.
- Конфликты синхронизации не обнаруживаются: копия `*.sync-conflict-*`
  лежит рядом с исходным файлом, и разбирать её приходится вручную.
- Поиск и фильтрация списков выполняются в памяти интерфейса.
- Сколько и какие данные хранит инструмент, решается отдельно для каждого;
  это решение задаёт только носитель (файлы в папке профиля) и правила записи.
- Если данных когда-нибудь станет много, SQLite вернётся **как локальный
  производный индекс** в `local/`: он не синхронизируется и перестраивается
  из файлов.
- Проверка записи при старте расширяется: корень, `local/` и папка активного
  профиля.
- Старые файлы в корне (`settings.json`, `logs/`) не переносятся: приложение
  ещё не выпущено, данных там нет.

## Отклонённые альтернативы

- **SQLite в синхронизируемой папке.** Файловая синхронизация рвёт
  транзакции, конфликт базы — потеря всех изменений второй машины.
- **SQLite только локально.** Данные инструментов разъезжаются по машинам,
  хотя смысл профиля — общий набор списков.
- **Один большой JSON на профиль.** Любое изменение переписывает весь файл,
  а конфликт затрагивает сразу все сущности.
- **`localStorage` браузера.** Живёт в профиле webview, то есть вне папки
  программы, — нарушение переносимости.
- **Логи по профилям.** Причину «профиль не открылся» некуда записать:
  лог этого профиля и есть то, что не открылось.
- **Проверка `.stfolder` и `.stignore` при старте.** Это диагностика для
  разработки: пользователь синхронизирует папку своими средствами, и
  программа не должна следить за чужим инструментом и давать советы о нём.
- **Отдельный реестр профилей (`profiles.json`).** Дублирует содержимое
  папки и создаёт ещё один файл, который может разойтись с реальностью.
