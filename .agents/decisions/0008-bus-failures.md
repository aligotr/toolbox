# ADR 0008: Отказы шины — что в лог, что в журнал

- **Статус:** принято
- **Дата:** 2026-11-12
- **Область:** `src-tauri/src/core/infra/bus.rs`, `src-tauri/src/lib.rs`,
  `src/core/infra/journal.ts`

## Контекст

В шине восемь мест, где что-то может пойти не так. Часть отказов возвращается
вызывающему (таймаут, неизвестный топик), часть проглатывается — и именно
вторая группа не оставляет следа.

Сегодня проглатывается:

- паника обработчика, поймано `catch_unwind`;
- потеря данных при сериализации в JSON (`unwrap_or(Value::Null)`);
- недоставка события в интерфейс (`TauriSink::emit`);
- событие, не вставшее в очередь (шина остановлена).

Пользователь в этих случаях видит только «ничего не произошло» и не знает, что
надо открыть лог. Отладка, к которой нет входа, бесполезна.

## Решение

1. **Записывать в файловый лог — все проглатываемые отказы.**

| Отказ | Уровень |
|---|---|
| паника обработчика события | `error` |
| ошибка сериализации события в JSON | `error` |
| не удалось отправить событие в интерфейс | `error` |
| событие не встало в очередь (шина остановлена) | `error` |
| таймаут `ask` | `warn` |
| неизвестный топик события или команды | `warn` |
| ответ после таймаута, промах корреляции | `debug` |

2. **Показывать в журнале — только то, что иначе осталось бы незамеченным.**
Шина отправляет событие `core:error` напрямую в приёмник, минуя очередь, как и
трасса. Журнал показывает короткую строку вида «обработчик `core:ping` упал»,
подробности остаются в файле лога.

В `core:error` попадают: паника обработчика, потеря данных при сериализации,
недоставка в интерфейс, потеря события из-за остановленной шины.

3. **Возвращённые ошибки не дублируются.** Таймаут и неизвестный топик уже
приходят вызывающему и попадают в журнал из места вызова (так делает
`HomeView`). Второй канал для них не нужен.

4. **«Нет подписчиков» — `debug`, а не `warn`.** Событие, опубликованное только
ради журнала, подписчиков в Rust не имеет по замыслу. Предупреждение на
нормальной работе приучает не читать лог.

5. **Модули паники не ловят.** Их ловит шина и сообщает о них через `core:error`,
   поэтому обработчик не обязан думать о диагностике.

## Почему так

Правило «лог читают после поломки» работает только если поломку видно. Разница
между «тихо сломалось» и «тихо работает» для пользователя неразличима, поэтому
один канал обязан быть в интерфейсе, а второй — содержать причину.

Разделение по признаку «возвращается ли ошибка вызывающему» держит журнал
чистым: он не превращается в удвоенный лог.

`core:error` идёт мимо очереди: если причина отказа — сама шина (остановлена,
потеряла событие), отправлять сообщение через неё бессмысленно.

## Последствия

- Появляется топик `core:error`, который модули не публикуют, а только
  слушает журнал.
- Уровень `warn` на «нет подписчиков» понижается до `debug` — лог перестаёт
  шуметь на штатной работе.
- Ошибки интерфейса и ошибки шины визуально различаются в журнале: первые
  пишет место вызова, вторые приходят от ядра.
- Стоимость — около пятнадцати строк в `bus.rs` и `lib.rs`.

## Отклонённые альтернативы

- **Только лог, без журнала.** Пользователь не узнает об отказе, пока не
  догадается открыть файл, а догадаться не из чего.
- **Только журнал.** Причина отказа теряется: в журнале нет места для backtrace
  и деталей сериализации.
- **`core:error` через шину как обычное событие.** Причина отказа может быть в
  самой шине; к тому же это лишний проход по очереди ради диагностики.
- **Показывать в журнале все восемь отказов.** Таймаут и неизвестный топик уже
  видны вызывающему; дублирование делает журнал шумным.
- **Оставить `warn` на «нет подписчиков».** Ложные предупреждения обесценивают
  уровень целиком.
