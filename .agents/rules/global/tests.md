# Принципы написания тестов

## Приоритет этих правил

Эти правила определяют процесс и объём тестирования в проекте и главнее любых
методологий из skills (включая TDD-подходы, генераторы тестов, требования к
покрытию).

Если skill предлагает: писать тесты до реализации, добиваться полного покрытия,
создавать тест на каждое значение или генерировать тесты массово — это
игнорируется в пользу этих правил.

Источник числа тестов — классы эквивалентности и согласованный с пользователем
список, а не методология skill.

## Когда писать тесты

Тесты пишутся после реализации бизнес-функции. Окончательное поведение
механизма и понимание его работы формируются в ходе реализации, поэтому тест
фиксирует уже сложившийся, а не предполагаемый контракт.

Тест отражает фактическое наблюдаемое поведение готового механизма. Если в ходе
написания тестов обнаруживается, что поведение реализации неверно — исправляется
реализация, а не подгоняется ожидаемое значение под текущий вывод.

## Что проверяет тест

Тест проверяет один бизнес-механизм по схеме вход → выход. Проверяется
наблюдаемый результат, а не способ его получения.

## Источник ожидаемого значения

Ожидаемое значение задаётся литералом в коде теста.

Ожидаемое значение нельзя получать из вывода тестируемого кода и нельзя
вычислять той же формулой, которая тестируется. Если ожидаемое значение
невозможно задать литералом без повторения тестируемой логики — это сигнал, что
механизм не имеет проверяемого поведения и тест не нужен.

Ожидаемые значения для нетривиальных расчётов подтверждаются пользователем, а не
выбираются агентом самостоятельно.

## Что тестировать, а что нет

Тестируется код, в котором есть ветвление, вычисление, преобразование данных или изменение состояния.

Не тестируется: код без ветвлений и вычислений (прямой проброс значения,
геттеры, конструкторы без логики); сторонний и сгенерированный код; то, что
уже гарантирует система типов или компилятор.

## Изоляция

Проверяй только вход и возвращаемый результат. Не проверяй приватные методы,
порядок внутренних вызовов и промежуточное состояние.

## Моки

Бизнес-логику не мокать.

Если тестируемый механизм зависит от другого собственного механизма с
бизнес-логикой — этот механизм не мокается, он участвует в тесте как есть.

Разрешено мокать внешние системы: сеть, время, файловая система, сторонние API.

Базу данных мокать запрещено без явного разрешения пользователя. Если механизм
требует БД: запроси разрешение мокать; при отказе или молчании запроси
разрешение на тестовую БД; используй только тестовую БД, production запрещена;
при отсутствии любого разрешения тест не пишется, пропуск фиксируется с
причиной.

## Граничные случаи

Покрывай граничные случаи бизнес-логики: пустые данные, ноль, граничные
значения, недопустимые состояния, переходы состояний.

## Объём тестов

Число тестов определяется числом классов эквивалентности входных данных, а не
стремлением к покрытию. Класс эквивалентности — набор входов, которые механизм
обрабатывает одинаковым путём. На один класс эквивалентности — один тест.
Значения из одного класса не размножаются в отдельные тесты, а объединяются в
параметризованный тест.

Перед написанием тестов составь список сценариев в формате
«класс входа → ожидаемый выход». Для каждого пункта укажи обоснование: какой
класс эквивалентности он покрывает и чем отличается от уже включённых. Пункт без
отдельного класса эквивалентности в список не добавляется.

Список сценариев согласуется с пользователем до написания тестов. Пиши тесты
строго по согласованному списку. Один пункт списка — один тест или одна строка
параметризованного теста.

Если в ходе реализации появился новый класс входных данных, список дополняется
и повторно согласуется, а не расширяется тестами самостоятельно.

## Форма

Одно поведение на тест. Имя теста описывает механизм, вход и ожидаемый результат.
Вариации входа объединяются в один параметризованный тест.

Один сценарий с одним входом не дублируется несколькими тестами.

## Метрики

Покрытие (coverage) не является целью и не доказывает качество. Качество теста
определяется способностью обнаруживать дефекты, что измеряется мутационной
проверкой.
