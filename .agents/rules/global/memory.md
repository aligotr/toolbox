# Память проекта: ADR, глоссарий, скилы

Здесь хранятся **решения**, которые нельзя восстановить из кода: почему сделано
именно так, что отвергли и какие последствия приняли. Код показывает «как»,
память проекта объясняет «почему».

## Структура

```text
.agents/
├── GLOSSARY.md            — общий язык проекта: термины и их значения
├── decisions/             — архитектурные решения (ADR)
│   ├── 0001-....md
│   └── 0002-....md
├── rules/                 — правила агентов: global и project
└── skills/                — скилы агента, управляются установщиком
```

Корневой `AGENTS.md` ведёт в правила. Этот файл — часть глобальных правил:
правила проекта ссылаются на него, чтобы агент читал память в начале работы.

## Как записывать решение

Одно решение — один файл в `.agents/decisions/`. Формат — ADR (Architecture
Decision Record). Номер выдаётся по порядку и **не переиспользуется**, даже
если решение отменено.

Имя файла: `NNNN-краткое-название.md`, только строчные буквы и дефисы,
например `0004-storage-layout.md`.

Шаблон:

```markdown
# ADR 0001: Название решения

- **Статус:** предложено | принято | заменено (ADR NNNN) | отклонено
- **Дата:** ГГГГ-ММ-ДД
- **Область:** какие файлы/подсистемы затрагивает

## Контекст

Какая задача стояла, какие ограничения действовали, что именно болело.

## Решение

Что решили — в утвердительном наклонении, без «может быть».

## Почему так

Ключевые аргументы. Здесь же — что произойдёт, если сделать иначе.

## Последствия

Что становится проще, что сложнее, какие правила теперь обязательны.

## Отклонённые альтернативы

Варианты, которые рассматривали, и причина отказа. Это самая ценная часть:
без неё через месяц всё придётся передумывать заново.

## Ссылки

- код: `путь/к/файлу`
- связанные решения: ADR NNNN
```

### Правила

1. **Запись неизменяема.** Принятое решение не переписывают. Если оно
   устарело — создают новое ADR, а в старом меняют только статус на
   «заменено (ADR NNNN)».
2. **Одно решение на файл.** Так на него можно сослаться из кода и обсуждения.
3. **Пишем «почему», а не «что».** Пересказ кода не нужен: код и есть код.
4. **Фиксируем отклонённые варианты.** Иначе спор возникнет повторно.
5. **Ссылки на код обязательны.** Решение без привязки к файлам быстро
   расходится с реальностью.

### Когда писать ADR

- выбор библиотеки, протокола, формата данных;
- границы модулей и правила взаимодействия;
- модель жизненного цикла (запуск, завершение, трассировка);
- неочевидное ограничение, из-за которого пришлось отступить от «красивого»
  решения;
- любое решение, которое дорого менять позже.

Не пишем ADR на локальный рефакторинг и на то, что очевидно из кода.

## Глоссарий

`.agents/GLOSSARY.md` — единый словарь проекта. Если термин в коде, интерфейсе
и обсуждении называется по-разному, побеждает глоссарий. Новый термин
добавляем туда сразу, как только он появился в коде.

## Скилы

`.agents/skills/` — каталог скилов, если проект их использует. Управляется
установщиком (lock-файл лежит в корне). Вручную не редактируем: обновление
перезапишет файлы. Свои скилы держим отдельно и подключаем конфигурацией
агента, чтобы обновление их не затёрло.
