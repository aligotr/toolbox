# 09. Профили

Blocked by: 06

**Статус:** сделано.

## Задача

Ввести профили как папки `profiles/<id>/` с переключением через перезапуск.

## Объём

- `profile.json`: `{ "version": 1, "title": "Работа" }`; имя папки —
  стабильный id без кириллицы.
- Список профилей — содержимое `profiles/`; отдельного реестра нет.
- Активный профиль — в `local/settings.json`.
- Меню профиля внизу сайдбара: список, активный отмечен, пункт
  «Управление профилями» открывает настройки на разделе «Профили».
- Создание (id из названия, конфликт — суффикс), переименование (меняется
  `title`, папка не двигается), удаление в `local/trash/<id>/`.
- Переключение: записать активный, перезапустить приложение; при старте
  все сервисы читают папку активного профиля.
- Профиль по умолчанию `work` создаётся при первом запуске.

## Как выполнено

- Rust `core/profiles.rs`: `list`, `create`, `rename`, `delete`,
  `ensure_default`, `validate_id`. Список — содержимое папки: отдельного
  реестра нет, поэтому профиль, скопированный на другую машину или созданный
  руками, виден без правки файлов.
- `validate_id` — одно правило на всю программу. Идентификатор становится
  именем папки, поэтому разрешены латиница, цифры, `-` и `_`; кириллица
  и разделители пути отбрасываются. `settings.rs` больше не держит свою
  копию проверки, а вызывает `profiles::validate_id`: два мнения о допустимом
  имени разошлись бы, и настройки приняли бы профиль, которого сервис
  профилей не видит.
- Создание из названия: транслитерация в id («Дом и семья» → `dom`),
  конфликт — числовой суффикс (`rabota`, `rabota-2`). Название хранится
  в `profiles/<id>/profile.json` (`{ "version": 1, "title": "…" }`),
  переименование меняет только его — папка остаётся на месте.
- `ensure_default` создаёт `profiles/work` при первом запуске. Отдельно
  обработан след прежней версии: пустая папка `work` без `profile.json`
  получает название, данные не трогаются.
- Удаление — перемещение в `local/trash/<id>/`. Корзина лежит в `local/`,
  а не в `profiles/`: удаление — решение этой машины, и чужая копия не должна
  получать чужую корзину; внутри `profiles/` папка `trash` ещё и выглядела бы
  профилем. Активный профиль удалить нельзя — отказ
  «Нельзя удалить активный профиль: сначала переключитесь на другой»:
  папка открыта работающим приложением.
- Старт (`lib.rs`): настройки читаются до пробы записи, потому что активный
  профиль определяет, какую папку проверять. Если папки из `settings.json`
  нет (настройки с другой машины, профиль удалили, синхронизация не донесла),
  выбирается `work`, иначе первый по названию; выбор пишется в журнал
  (WARN в логе) и сохраняется в `settings.json`. Молча создать пустую папку
  с тем же именем значило бы показать пустое приложение вместо данных, которые
  лежат рядом. Пустой `profiles/` — законный первый запуск: активным становится
  `work`.
- `Settings.active_profile` — раздел схемы, а не отдельный файл: переключение
  идёт через `settings_set`-механику и пишет только свой раздел, не затирая
  чужие правки.
- `profile_switch` только пишет настройку. Перезапуск — отдельная команда
  `app_restart` через `request_restart`, а не `restart`: выход обязан пройти
  общий путь `RunEvent::Exit`, где дописываются геометрия окна и файл лога.
  Интерфейс успевает сбросить рабочее пространство между двумя вызовами.
- TS `core/profiles.ts`: состояние списка и гранулярные
  `status.<операция>.loading/error`; ошибка не стирает уже показанный список —
  пустое меню выглядело бы потерей данных. `switchProfile` сначала вызывает
  `flushWorkspace()`: перезапуск не проходит через обработчик закрытия окна,
  и отложенная запись иначе пропала бы вместе с процессом.
- `shell/useProfiles.ts` — общие подтверждения переключения и удаления.
  Спрашивать по-разному в меню сайдбара и в настройках значит однажды забыть
  подтверждение в одном из мест.
- `shell/ProfilesSection.vue` — список, создание, переименование, удаление
  и переключение в настройках. `shell/Sidebar.vue` — подвал-кнопка
  с названием активного профиля и popup-меню: профили (активный отмечен
  и недоступен), разделитель, «Управление профилями». Пункт неактивного
  профиля сразу открывает подтверждение перезапуска.
- Рабочее пространство остаётся общим в `local/`: ADR 0011 не делит его
  по профилям. Профиль разделяет шаблоны и данные инструментов.

## Проверено

- `cargo test --lib` — 65 тестов (13 на профили), `cargo check` — без
  предупреждений, `npm run build` — 258 модулей.
- В живом окне Tauri (WebView2 DevTools, настоящие клики по интерфейсу):
  - первый запуск создал `profiles/work` с `{ "title": "Работа" }`;
  - создание «Дом» → папка `dom`, журнал: «создан профиль «Дом» (dom)»;
  - переименование «Дом» → «Дом и семья»: папка `dom` не изменилась;
  - повторное «Работа» → `rabota` (конфликт имён разрешён суффиксом);
  - удаление активного профиля отклонено с текстом отказа, список цел;
  - удаление `rabota` унесло папку в `local/trash/rabota`, строка исчезла
    из списка, журнал записал путь;
  - отмена в подтверждении переключения оставила `active_profile: "work"`;
  - переключение на `dom` перезапустило приложение: новый процесс, в логе
    путь `profiles\dom`, в `settings.json` `active_profile: "dom"`,
    в сайдбаре «Дом и семья»; переключение обратно записало `work`;
  - `active_profile: "ghost"` в `settings.json` → WARN в логе о ненайденном
    профиле, настройка исправлена на `work`, сайдбар «Работа», оба профиля
    на месте;
  - «Управление профилями» в меню профиля открывает вкладку «Настройки»
    с разделом профилей.

Изоляцию данных двух профилей проверить пока нечем: своих данных у сервисов
ещё нет. Папка профиля доказана путями в логе и командами; фактические
данные появятся в тикетах 10 и 12 и будут проверены там.

## Готово, когда

- Два профиля не видят данных друг друга.
- Удалённый профиль исчезает из списка и лежит в `local/trash/`.
- Перезапуск с другим профилем открывает его шаблоны и данные.
