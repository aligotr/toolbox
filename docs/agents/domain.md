# Domain docs

Как инженерным скилам читать доменную документацию этого проекта.

## Перед изучением кода прочитай

- **`.agents/GLOSSARY.md`** — единый словарь проекта.
- **`.agents/decisions/`** — принятые архитектурные решения (ADR). Читай те,
  что затрагивают область работы.

Файлов `GLOSSARY.md` и `docs/adr/` в корне нет и не должно появляться:
глоссарий и ADR живут только в `.agents/`. Если скил их не нашёл — работать
молча, не предлагать создать.

## Структура

Проект single-context: один глоссарий и один каталог решений на весь
репозиторий. `GLOSSARY-MAP.md` не используется.

## Используй словарь глоссария

Когда в выводе появляется доменное понятие (заголовок тикета, предложение по
рефакторингу, гипотеза, имя теста), используй термин в том значении, которое
задаёт `.agents/GLOSSARY.md`. Не подменяй синонимами, которые глоссарий
разводит.

Если нужного понятия в глоссарии нет — это сигнал: либо язык придуман и его
надо пересмотреть, либо пробел реальный и его закрывает `domain-modeling`.

## Конфликт с ADR

Если вывод противоречит действующему ADR — скажи об этом прямо, а не
переопределяй молча:

> _Противоречит ADR 0001 (модель шины), но стоит пересмотреть, потому что…_
